# Prompt Test Spec v0.1

Status: draft

This document defines the first structured spec format generated by `agentest create`.
The format is intentionally simple and readable.
It should be the stable storage format for customer-authored prompt contract tests.

## Design Goals

- easy to read in code review
- easy to generate from natural language
- easy to map onto the current runner and assertion engine
- points to the real prompt source instead of duplicating prompt content when possible
- fits naturally inside an existing prompt-driven repository

## File Location

Generated specs may live under:

```text
.agentest/tests/*.agentest.yaml
```

But the embedded path should also support standard repository locations such as:

```text
tests/**/*.agentest.yaml
src/**/tests/*.agentest.yaml
src/prompts/**/*.agentest.yaml
```

The important rule is not the directory name.
The important rule is that specs can stay close to the project they validate.

## Example

```yaml
version: 0.1
name: release-note-stability
description: Ensure the release-note prompt always reads the feature spec, reads the bug report, and submits a concise release note.
tags:
  - release-note
  - claude

agent:
  preset: claude

promptSource:
  kind: module
  ref: ./src/prompts/release-note.ts#buildPrompt
  args:
    featureName: checkout-v2
    bugId: checkout-null-name

execution:
  timeoutMs: 60000
  stability:
    runs: 5
    minPassRate: 0.8

mocks:
  - tool: get_feature_spec
    when:
      name: checkout-v2
    returns: |
      Feature: checkout-v2
      Behavior: display names should be trimmed before rendering.
      Fallback: when a display name is missing, use "Anonymous".

  - tool: get_bug_report
    when:
      id: checkout-null-name
    returns: |
      Bug ID: checkout-null-name
      Observed failure: checkout crashes when user.name is undefined.
      Suggested fix: null-safe trim and fallback string.

  - tool: submit_release_note
    returns:
      accepted: true
      id: release-note-001

assert:
  tools:
    required:
      - get_feature_spec
      - get_bug_report
      - submit_release_note
    sequence:
      - get_feature_spec
      - get_bug_report
      - submit_release_note
    only:
      - get_feature_spec
      - get_bug_report
      - submit_release_note
    noUnmatchedCalls: true
    calls:
      - tool: submit_release_note
        times: 1
        with:
          summary:
            regex: Anonymous|null-safe|undefined

  process:
    exitCode: 0
    timeout: false
    durationMsMax: 60000

  output:
    stdoutContains:
      - Anonymous
```

## Top-Level Fields

### `version`

Required.
The first supported value is `0.1`.

### `name`

Required.
Human-readable test name.

### `description`

Optional.
Freeform explanation for review and maintenance.

### `tags`

Optional.
Used by `agentest run --tag <name>`.

### `agent`

Optional.
Overrides the default preset from `.agentest/config.json` when needed.

Supported fields:

- `preset`: `claude` or `copilot`

## `promptSource`

Required.
Defines where the prompt comes from.

Supported kinds:

### `kind: inline`

Stores the literal prompt in the spec.
Useful for quick ad hoc tests.

Example:

```yaml
promptSource:
  kind: inline
  text: Read the bug report and submit a concise release note.
```

### `kind: file`

Loads the prompt from a file.

Example:

```yaml
promptSource:
  kind: file
  path: ./prompts/release-note.md
```

### `kind: module`

Imports a module and calls an exported function.
This is the preferred shape for prompt-as-code projects.

Example:

```yaml
promptSource:
  kind: module
  ref: ./src/prompts/release-note.ts#buildPrompt
  args:
    featureName: checkout-v2
```

### `kind: command`

Runs a local command and uses stdout as the prompt.
Useful when prompts are generated by a build step.

Example:

```yaml
promptSource:
  kind: command
  command: node
  args:
    - ./scripts/build-prompt.js
    - release-note
```

## `execution`

Optional.
Controls runtime behavior.

Fields:

- `timeoutMs`
- `stability.runs`
- `stability.minPassRate`

If omitted, values come from `.agentest/config.json`.

## `mocks`

Optional but expected for most tests.
Each item describes one mocked tool behavior.

Fields:

- `tool`: required tool name
- `when`: optional argument matcher
- `returns`: optional return payload
- `throws`: optional error string

Exactly one of `returns` or `throws` should be present.

Example:

```yaml
mocks:
  - tool: get_bug_report
    when:
      id: checkout-null-name
    returns: |
      Bug ID: checkout-null-name
      Suggested fix: null-safe trim and fallback string.
```

## Matcher Grammar

The spec format needs a YAML-native matcher representation.
The first version should support these shapes:

- exact values
- nested object matching
- regular expression matching
- substring matching
- anything matcher

Examples:

```yaml
with:
  summary:
    regex: Anonymous|null-safe|undefined
```

```yaml
with:
  path:
    contains: user-service
```

```yaml
with:
  metadata:
    anything: true
```

Interpretation rules:

- plain scalars mean exact match
- plain objects mean nested object match
- `{ regex: "..." }` maps to a regular expression
- `{ contains: "..." }` maps to string containment
- `{ anything: true }` means any defined value

## `assert`

Optional but expected for most tests.
Assertions are grouped into three areas.

### `assert.tools`

Fields:

- `required`: list of tools that must be called
- `sequence`: ordered subsequence that must appear
- `only`: exact allowed tool set
- `noUnmatchedCalls`: boolean
- `calls`: per-tool argument or count checks

Example:

```yaml
assert:
  tools:
    required:
      - read_spec
    calls:
      - tool: read_spec
        times: 1
```

### `assert.process`

Fields:

- `exitCode`
- `timeout`
- `durationMsMax`

### `assert.output`

Fields:

- `stdoutContains`
- `stderrContains`
- `stdoutNotContains`
- `stderrNotContains`

## Mapping To The Current Engine

This spec is intentionally close to the current JS DSL:

- `mocks[*]` maps to `t.mock(...).when(...).returns(...)`
- `assert.tools.required` maps to `toHaveCalledTool(...)`
- `assert.tools.sequence` maps to `toHaveToolSubsequence(...)`
- `assert.tools.only` maps to `toOnlyCallTools(...)`
- `assert.process.exitCode` maps to `toExitWithCode(...)`
- `assert.output.stdoutContains` maps to `toContainStdout(...)`

The implementation strategy should be:

1. parse YAML spec
2. resolve `promptSource` into a concrete prompt string
3. translate the spec into the existing `AgentTestContext` calls
4. reuse the current runner, mock server, and assertion engine

That keeps the new product layer thin and lets the current engine remain the source of truth.

## Out Of Scope For v0.1

- custom JavaScript hooks
- loops and branching in the spec
- cross-test shared fixtures
- auto-recorded sessions
- automatic prompt rewriting

The first version should optimize for clarity, stability, and a direct mapping onto the current runtime.
